# Test harness

Scripted play for the milestones that need playing (spec sections 6 and 7): a script drives the client through its control socket ([PROTOCOL.md](../native/control/PROTOCOL.md)), and each step is confirmed in the test server's SQL logs and by captured frames. Python 3, standard library only.

```bash
python3 port/harness/run.py --self-test                      # harness tests: mock client + one read-only server check
python3 port/harness/run.py port/harness/scripts/login.py --mock
BF_CLIENT=<client binary> python3 port/harness/run.py login  # the real test (server must be online)
BF_APP=<path>/Bifrost.app python3 port/harness/run.py gate   # the same, the bundle launched as Finder does (M12.1)
python3 port/harness/run.py --server-status
```

A run prints one line per step and writes `build/harness/<script>[-mock]-<time>/` with `report.json`, `report.md`, the client's trace, packet log, stdout and the control transcript; the latest report is also copied to `build/harness/<script>[-mock]-latest.{json,md}`. The exit status is 0 when every step passed.

## Rules the harness keeps

- **The server is shared.** `ensure_up` starts it only when it is not running, from the main checkout's `port/server` (or `BF_SERVER_DIR`), since a worktree's copy would remount the fixed compose project. `restart` restarts the `rathena` service only and refuses unless called with `allow=True` or `BF_SERVER_RESTART=1`: it drops every connected session, so it is for the lead after a configuration change.
- **Frames stay out of git.** Real runs capture under `<game folder>/test/frames/<script>/` (`BF_FRAMES_DIR` overrides); the script's `MANIFEST` path in the repository gets `<sha256>  <w>x<h>  <name>.png` lines, nothing else. Mock runs write their synthetic frames under `build/harness/frames-mock/` and their manifest into the run directory.
- **Evidence windows.** `t.logs.mark()` before an action records the database clock and the highest id of every log table; readers take `after=marker` and select by id, which is exact. `loginlog` has no id and is selected by time (one-second granularity).
- **Set-up versus play.** SQL set-up (`Accounts.create_account`, `Accounts.set_char`) is for the scene before the client logs in: it refuses an online character, because the map server overwrites the row at every save. Once in game, set-up is by atcommand, typed by the client (`t.gm.run(GM.warp(...))`) and so logged in `atcommandlog`; it needs a group-99 account (`bfadmin`, or `create_account(..., group_id=99)`). The action under test is always played through the client.
- **Socket path.** macOS limits a socket path to 103 bytes; the socket lives in `build/harness/sock/`, or in the system temporary directory when that path is too long.
- **Debug defaults do not apply.** A debug build opens a control socket and keeps a rolling trace in `<support>/Logs` without being asked (PROTOCOL.md section 1). A harness launch always passes `--control`, `BF_CONTROL` and `BF_TRACE_FILE`, which win, so it gets neither, and its own `BF_HOME` keeps it away from the user's folders. By hand: `open -n <build>/<name>.app` with a debug build gives a socket at `~/Library/Application Support/<name>/control-main.sock` (`--env BF_HOME=<dir>` moves it under that home), and `trace-<date>-<time>-<pid>.txt` beside it in `Logs`.

## Launching the bundle

`BF_APP=<build>/<name>.app` (built by the target `app`, `cmake --build --preset debug`) makes every script launch the bundle the way Finder does (M12.1), with no change to the script:

- **Through LaunchServices:** `open -n <bundle> --args --control <socket> <script args>`, run from `/` with only `HOME`, `USER` and `LOGNAME` in `open`'s own environment. The client therefore gets launchd's environment, as from Finder: `/` as working directory, the system `PATH`, no terminal. `-n` starts a new process even while another copy of the bundle runs. The client's own single-instance check still applies, and Finder's double-click would bring the running copy to the front instead.
- **The harness's variables** travel by `open --env`: `BF_TRACE` (always with `mode`, see below), `BF_TRACE_FILE`, `BF_PKT_LOG`, `BF_CONTROL`, `BF_WINDOW_SCREEN`, `BF_MUTE` (1 unless the environment sets it: test clients make no sound; `BF_MUTE=0` to listen), whatever the script passes (`BF_HOME`, ...), and every `BF_*`, `ASAN_*`, `UBSAN_*`, `TSAN_*`, `LSAN_*` variable of the harness's own environment.
- **The game folder comes from the settings,** as if it had been chosen in the chooser: when the launch has its own `BF_HOME` (`play.own_home` and the scripts' own homes), the harness writes `Paths/GameFolder` into that home's `Settings.plist` and does not pass `BF_CLIENT_DIR`. A value the script stored is kept, and a `BF_CLIENT_DIR` the script passes itself (intro's folder E) is passed. `BF_APP_FOLDER=links` stores a folder of symbolic links to the game folder's entries, made as `<run>/game`, so that the trace line `start: ..., game folder <run>/game` can only have come from the setting. A launch without its own home (none of gate, granny, intro) gets `BF_CLIENT_DIR`, so that the user's real settings are never written.
- **The game folder is checked** in every mode, bundle or bare binary, `links` or a path: the trace's first line `start: ..., game folder <path>` must name the folder the harness stored (`Paths/GameFolder`) or passed (`BF_CLIENT_DIR`), or `connect` fails the launch (`the client uses the game folder X, not the one the harness stored: Y`), so a client that silently uses another folder (the default `~/Games/<name>`) fails its script. Not checked for the mock, or for a bare binary whose `BF_TRACE` lacks `mode`. A client that refuses its folder exits before its socket; the error names its refusal line (`... before opening its socket: prefs: configured game folder is not usable: The folder's path is N bytes long; ...`). The game folder's path may be at most `BF_FILE_FOLDER_MAX` (768) bytes (port/native/sys README, "Long paths"); for a refusal run with the bundle pass `BF_NO_ALERTS=1`, so that the chooser's panel is not opened.
- **The process** is launchd's child, and `open -W` cannot wait for it on this macOS ("Unable to block on application"). The harness therefore takes the new process running the bundle's executable (`ps`), confirmed by the `pid` of `hello`, checks it with `kill(pid, 0)`, and stops it by signal when it overstays. The exit status is read from the trace line `exit: WinMain returned N`, which the client writes on every orderly exit, or `exit: start refused, status N (...)` when the start ends before `WinMain` (a refused game folder, the chooser cancelled). A client that vanished without that line has the status `None`, which fails the runner's "client exits cleanly" step. Stdout and stderr go to `client-stdout.txt` (`open --stdout/--stderr`); each launch's command line is appended to `launch.txt` in the run directory.

## For the client's control module

The scripts use only what PROTOCOL.md specifies. Where they click a control they use these `controls` ids, which the control module has to report (or the scripts change with it): `LOGINWND` `id_edit`, `pw_edit`, `ok`; `SELECTCHARWND` `slot:<n>` (text = character name), `ok`, `make`; `MAKECHARWND` `name_edit`, `ok`; `CHOOSESELLBUYWND` `buy`, `sell`; `ITEMSHOPWND` and `ITEMSELLWND` `item:<item id>`, `ok`; `CHOOSEWND` `choice:<label>`; `QUITWND` (Escape for a living character, `UIQuitWnd`) `restart` (character select), `exit`, `cancel`; `RESTARTWND` (Escape for a dead character, `UIRestartWnd`) `restart` (save point), `to_character_select`, `quit`, `cancel`. Login, character selection and creation go by keyboard only (Tab, Enter, arrows), so the M5 scripts work even while `controls` is empty. The real client reports these and more (all controls of a window, named after their control ids; the list is in [client/src/README.md](../client/src/README.md), `bf_client_state.cpp`).

## Open

- The map load after `CZ_ENTER` belongs to M6.1; `charselect.py` and `autologin.py` record the client's exit after zone entry instead of judging it (`stop_after_zone_entry`); `--param strict_exit=1` judges it again.
- "Save" with the Keychain is untested while the login keychain is locked (unattended run): the client then stores the account only and traces `sys: keychain not available`.

- The gate test's Job Master is rAthena's `npc/custom/jobmaster.txt`, which the stock configuration does not load: `port/server/import/map_conf.txt` needs `npc: npc/custom/jobmaster.txt`.
- The map server saves a character on logout, map-server change and every `autosave_time` (300 s in `map_athena.conf`); the scripts read positions from `chatlog` while playing and from `char` only after quitting.
- The mock's picking is a flat grid; it checks the harness, not the client's camera.

The M6 scripts run the client with `BF_HOME` in the run directory (`play.own_home`), so they start from default window positions and leave the user's settings alone; `bfharness/bot.py` runs `bifrost-bot` (build it with `port/bot/build.sh`) as a second player.
